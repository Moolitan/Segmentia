# Final MCP Server Spec for Issue Tracker  

## 1. **Concise Spec**  
- **Tools**:  
  - `issue_query(id?, status?, assignee?, label?, updated_since?, limit<=100, cursor?)` → `{items, next_cursor, has_more}`.  
  - `issue_create(title, body, labels?, assignee?)` → issue object.  
  - `issue_comment_add(issue_id, body)` → comment object.  
- **Pagination**:  
  - `limit` clamped to 100 server-side; clients get a warning if they request more.  
  - All list responses include `next_cursor` (opaque token) and `has_more` (boolean) at the top level.  
- **Error Handling**:  
  - 4xx errors: Non-retryable, include field-level validation messages and explicit "fix and retry" instructions.  
  - 5xx errors: Retryable, include `attempt_remaining` count.  
  - Always return structured JSON; no free-text stacktraces.

## 3. **Top 3 Design Decisions**  
1. **Pagination Safety**:  
   - Hard-limit `limit` to 100 to prevent excessive data loads.  
   - Expose `next_cursor` and `has_more` explicitly to guide agents through large datasets.  

2. **Error Clarity**:  
   - 4xx errors must explicitly instruct agents to "fix the field and retry" (no silent loops).  
   - 5xx errors include `attempt_remaining` to avoid dead loops.  

3. **Tool Consistency**:  
   - All list responses use the same structure (`{items, next_cursor, has_more}`) for predictability.  
   - Tool names follow `verb_noun` convention (e.g., `issue_query`, `issue_comment_add`).
