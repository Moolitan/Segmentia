# Final Design Doc: Automatic Retry for Failed Benchmark Tasks

## Summary for Teammates
- **Problem**: Manual reruns of transient failures are time-consuming and error-prone.
- **Solution**: Bounded retries (3 for transient, 1 for cautionary) with exponential backoff.
- **Rollout**: Phased launch starting with dark-launch, then limited task types.
- **Risks**: Masking real bugs, resource spikes, and UI clarity challenges.
- **Validation**: Reader testing with Claude to ensure clarity and correctness.

## Full Document

### Background
The experiment platform currently requires manual reruns for failed tasks, leading to operator overhead. Three common failure patterns—transient timeouts, I/O errors, and logic bugs—highlight the need for automated retries that avoid masking real issues.

### Goals
- Automate retries for transient failures.
- Maintain traceability between original and retried runs.
- Prevent infinite retries for non-transient issues.

### Proposed Approach
- **Classifier**: Tag failures as `retryable_transient`, `retryable_with_caution`, or `non_retryable`.
- **Retries**: 3 attempts for transient errors (30s–5min backoff), 1 for cautionary errors.
- **Traceability**: Retries share the original task ID and log `retry_of`, `attempt_number`, and `failure_class`.

### Risks & Mitigations
- **Masked Bugs**: Conservative classifier rules + dashboard visibility of retry counts.
- **Resource Amplification**: Per-tenant retry budgets + global circuit breaker.
- **UI Clarity**: Explicit indicators for retried runs in dashboards.

### Rollout Plan
1. **Dark-launch** classifier for 1 week.
2. **Phase 2**: Enable retries for `web_retrieval` tasks, one tenant at a time.
3. **Phase 3**: Expand to all `retryable_transient` tasks after stability checks.

### Open Questions
- Classifier rule specifics (e.g., exception types for "transient").
- Ownership of retries if a worker restarts mid-retry.
- Dashboard integration for "retried N times" metrics.
