# SegKV 设计纲领:作为一篇系统论文,设计点应该怎么排?

## 这份文档怎么读

前面五份是**实验笔记**(记录我们测了什么、发现了什么)。这一份不一样,它是**设计纲领**
——把前面的发现收拢成"这篇论文要提出哪几个设计点"。名词第一次出现仍用大白话解释,
建议顺着读。每个设计点我都会连回对应的实验笔记,方便核对依据。

先把结论放最前面:

> 我们的端到端实验证明了**动机成立**(简单复用基本不坏输出)。但系统结构领域的论文,
> 光证明"动机对"不够,还要有一个**真正去修复问题的设计**。对照标杆论文 CacheSlide
> 的设计骨架,SegKV 的三个设计点应该是:**(1) 用免训练的方法解决位置(证明对手那套
> 要训练的位置编码不必要);(2) 用"按层深 + 中间存档"的方式修复内容,而不是像对手那样
> "按 token 挑"(因为我们已证按 token 在本场景失效);(3) 一个便宜的"影响预测器",
> 只在复用真会伤输出时才触发修复,平时直接复用。** 下面逐条讲清楚,并诚实说明其中的
> 张力和怎么解。

---

## 1. 为什么写这份纲领

我们在做的事:AI agent 反复用到同一段固定文字(叫一个 "skill"),我们把它的中间计算
结果缓存下来复用,省时间。

到目前为止(见前五份笔记):

- 复用带来的误差分两半——位置那半免训练就解决了;内容那半(深层的 V)坏得又宽又深。
- 但端到端看,简单复用已经让模型 84-95%(平均 92%)的输出决策保持不变。

所以"复用基本够用"这个**动机**很扎实。但正如评审视角会指出的:**一篇系统论文需要一个
真正的设计贡献(一套机制 + 系统实现 + 评测),不能只停在"动机对"。** 这份纲领就是把
发现转成设计点。

---

## 2. 先看标杆:CacheSlide 的设计点骨架

CacheSlide(FAST'26)和我们做同一件事(agent 跨位置复用 KV)。它的论文由**三个设计点**
撑起来,每个都遵循同一个模板:**针对一个明确的问题 → 一个有名字的机制 → 可测的系统
收益 → 落进真实系统(vLLM)**。

1. **CCPE(修位置)**:让"缓存时的位置"和"复用时的真实位置"对齐。机制是一种基于 CoPE
   的位置编码,**需要对模型做 LoRA 续训,并按单一任务统计高频位置模式**。
2. **WCA(修内容)**:补回固定段和变化段之间的注意力。机制是**按 token 选择性重算**——
   先量每个 token 偏差、挑偏差最大的一批重算、用权重和缓存融合、每几层检查一次、修好的
   踢出、换下一个最偏的。它的**核心假设是"坏掉的只集中在少数 token"**。
3. **SLIDE(系统)**:解决 KV 换出到硬盘时的读写开销。机制是读写解耦 + 脏页驱逐 + 写合并。

记住这个骨架:**位置 + 内容 + 系统,三件套。** 我们的设计点要对着它排。

---

## 3. 对照排 SegKV 的设计点

| 维度 | CacheSlide 怎么做 | SegKV 怎么做 | 依据(我们的发现) |
|---|---|---|---|
| 位置 | CCPE,**要 LoRA 续训** | **免训练 re-rotation**(把缓存的 K 重新旋转到新位置) | 笔记一:≤40k 内 re-rotation 把 K 相似度从 0.636 补到 0.900、V 完全不变 → **位置免训练就够**,CCPE 的训练不必要 |
| 内容(修 V) | WCA,**按 token 挑** | **按层深挑 + 中间存档**(浅层 KV 近无损直接复用;缓存 skill 在第 N 层的激活;从第 N 层续算深层,attend 真实前文) | 笔记三:本场景漂移**宽**(90%+ token 都坏)→ **WCA 的"集中在少数 token"假设失效**。笔记二:按层深的残差检查点能把深层 V 拉回 |
| 系统 | SLIDE(换出 I/O) | 让"按深度部分重算"在 vLLM 里高效:存什么(浅层 KV + 一个中间存档)、怎么触发与调度、显存怎么管 | 待设计 |

**这张表本身就是 SegKV 的故事**:同样是 agent 跨位置复用,但因为我们的场景是**跨任务、
整段前文都变**,漂移又宽又深;于是 CacheSlide 的两个核心机制在这里——**一个不必要
(位置不用训练)、一个失效(按 token 挑不管用)**。SegKV 改用"免训练旋转 + 按深度存档"
对症下药。

---

## 4. 必须正视的张力(否则设计点立不住)

有两个事实对"修 V"不利,要摆到台面上:

1. **按层深修,也只能省大约 30% 的计算**(因为坏在深层,大部分层还是得重算)。见笔记二。
2. **不修,端到端也有 92% 的输出决策是对的**。见笔记五。

合起来,评审会问一个尖锐的问题:**花 70% 的算力,去修一个不修也大体没事的东西,
图什么?** 如果设计是"对每一次复用都无脑做深度重算",这个问题答不上来。

---

## 5. 解法:把"修不修"做成自适应,按 skill 粒度

化解张力的关键,来自笔记五里一个被忽略的细节:**漂移在一个 skill 内部是宽的,但
"会不会真影响输出"在不同 skill / 任务之间差别很大**——web_artifact 这个任务分叉明显
(平均 KL 0.33、个别冲到 10.9),mcp 却几乎不分叉(0.03)。

这说明:**选择的正确粒度不是 token(CacheSlide 那样),而是"哪一次 skill 复用"。**

于是 SegKV 的设计可以是:

> **平时直接复用(最便宜);用一个便宜的"影响预测器"判断某一次 skill 复用会不会真正
> 伤输出;只对会伤的那几次,做按层深的中间存档重算。**

这样三个设计点就齐了,而且每个都对症、都和 CacheSlide 不同:

- **设计点一(位置)**:免训练 re-rotation。贡献=证明对手那套要训练的位置编码不必要。
- **设计点二(内容)**:按层深 + 中间存档修 V。贡献=证明对手"按 token 挑"在宽漂移场景
  失效,换成"按深度"这条轴。
- **设计点三(系统/自适应)**:skill 级的影响预测 + 按需触发 + 在 vLLM 里的高效实现。
  这是对应 CacheSlide 里 SLIDE 的那个"系统"位置,也是最有新意的点。

---

## 6. 下一步:支撑这套设计点要做的实验

1. **画"质量 vs 成本"的权衡曲线(Pareto)**:把几种做法放在一起比——直接复用(快、
   92%)、按层深修(存档放不同深度 N)、整段重算(慢、100%),并和 CacheBlend、
   CacheSlide 比,证明 SegKV 这条线在"同样质量下更快 / 同样速度下质量更好"。
2. **找"影响预测器"的便宜信号**:能不能用浅层的偏差、或 skill 的类型,提前判断"这一次
   复用会不会伤输出"。这是设计点三的核心,也是把张力转成贡献的关键。
3. **真实系统复核**:目前修复机制是在 HuggingFace 里模拟;最终要在真实 vLLM 上实现并测。
